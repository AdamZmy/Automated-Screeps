# Screeps World 房间管理模块重设计与实现

实现状态（2026-09-28）：已按用户审核设计重构，game build2026-09-28.1，16个职责模块加infrastructure兼容导出，共17个API受管模块。完整npm回归及独立审阅通过，发布与实际tick证据另见CURRENT_STATE/Issue13。下列旧版本主房快照是解释设计的历史样本，方案语言保留原审核语义，不作为实时状态。

## 设计目标与已确定规则

管理单元采用 Colony：一个自有主房，加上明确归属于它的外矿和经济设施。当前自有的两个房间分别是独立 Colony；支援关系不改变所有权。外矿是扩展接口，本提案不自动启动新的外矿业务。

采用轻量数据对象和普通函数，不引入通用任务树、深层继承或每个 creep 一整套对象包装。main 负责装配和顺序，业务模块各自持有状态；资源通过请求接口协调。宏观布局仍由 Codex 在本地完成，游戏运行时读取已审核执行档案。

必须保留的用户规则：

- 已有单位有能量、合法目标且在工作范围时连续工作；预算用于目标、人口、身体和补给优先级，不是每 tick 停工阀门。
- 真实积压可以支持有根据的库存消化；明确标记临时库存支出，不报告为可持续收入。
- 到达合法卸货目标后按实际可接收空位卸货；旧预约额度不能截断本可完成的整批交付。
- Controller Container 的全部物理空位都可以接收能源，不恢复人为高低补货水位。
- Rampart 停建。保留已有 Rampart 和布局坐标；修复已有防线是独立政策，不能从停建推导出拆除或停止一切维修。
- 暂停的巡检自动化保持暂停。代码中的每 tick 管理器与 Codex 自动化是两回事。
- 不在本提案中引入市场交易、进攻任务或修改既有扩张授权范围。
- 不新增无证据的人数、用能、施工并行硬上限。控制器等级、身体与孵化限制、可站位数、CPU 等游戏约束仍有效；已有人工限制在迁移时逐项标记、独立评审。

## 共享数据契约

所有请求是普通数据。请求列表、当前对象引用、当 tick 预留量放在 heap；只有跨 tick 执行状态进入 Memory。

| 数据 | 核心字段 | 所有者 |
| --- | --- | --- |
| RoomContext | tick、roomName、visible、colonyId、structuresByType、creepsByHome、creepsByPosition、sources、sites、threats | runtime；业务只读 |
| ColonyPolicy | phase、security、cpuMode、incomeEstimate、confidence、replacementNeeds、growthPriorities、stockDrawdownPlan、reason | colony |
| WorkforceDemand | id、owner、home、role、slotKey、target、requiredCapacity、capacityUnit、bodyConstraints、neededAt、expiresAt、reason | 业务模块发布；workforce 汇总 |
| LogisticsRequest | id、owner、nodeId、roomName、resource、offer/demand、amount、priority、deadline、expiresAt | 节点所属模块发布；logistics 分配 |
| CreepAssignment | creepName、owner、operationId、sourceId、targetId、phase、expiresAt、lastProgressTick | 唯一任务所有者 |
| ConstructionRequest | planVersion、position、type、rcl、purpose、dependencies、priority、enabled | planner 提供计划；development 决定创建 |
| ModuleResult | tick、status、reason、expectedEffect、errorCode | 执行模块；monitor 汇总 |

`home` 表示经济归属，`creep.room.name` 表示物理位置，`operationId` 表示当前行动。业务模块只写自己的持久状态；跨模块调整通过输出请求完成。恢复期临时换岗由 Colony 显式转移任务所有权，不让两个执行器同时接管同一 creep。

同一 tick 预期转入的能源不当作已经到账。预算、预计意图和真实事件分别保存，后者才进入实际产出指标。对同一资源的预测和预留只是协调工具，不改变 Game 快照。

## 1. main：调度与运行边界

**输入**：Game、Memory、各模块接口。**输出**：本 tick 的确定性调用顺序及故障记录。**持久状态**：仅版本和运行健康摘要；不保存业务规则。

逻辑：

1. 初始化 schema，建立共享索引；结算上一 tick 的真实事件。
2. 对所有可见自有房执行威胁判断与紧急防御，不在某个房的复杂规划后才轮到另一个房。
3. 更新必要的任务状态与 ColonyPolicy。死亡、敌袭、关键建筑消失等即时事件可以绕过低频经济重算间隔。
4. 各业务模块提出原始需求；Colony 协调优先级后，业务模块形成具体工作分配及资源需求。
5. workforce 统一安排出生；links 与 logistics 共享资源占用记录，形成不冲突的执行计划。
6. 执行矿工、工人、运输者和任务单位；每个 creep 只由一个任务所有者决定行为。兼容动作可以并行，冲突动作只能选择一种。
7. 完成必要移动与当 tick 结果登记，再运行可选评估和监控展示。

全局清理、模块、房间、creep 分别有异常边界。某模块失败时，不沿用不完整的新请求；核心单位仍可执行经过校验的已有任务或恢复动作。普通异常能隔离，CPU 强制中断不能靠 try/catch 解决：可选工作必须在必要动作之后，运行前检查剩余预算。

**频率**：必要流程每 tick；低频工作按事件和到期时间运行并按房间错峰。

**验收**：规划抛错时另一房的防御和矿工仍运行；global reset 后恢复；不存在同一 creep 的重复控制或同一 spawn 的成功意图覆盖。

## 2. runtime / RoomContext：统一观察与索引

**输入**：当前 Game、既有布局版本和对象 ID。**输出**：各模块共享的当 tick 数据视图。**持久状态**：必要 ID、版本、lastSeen；对象缓存可重建。

逻辑：

1. 每 tick 一次遍历全局 creep，建立归属、角色、当前位置和任务索引。
2. 对需要的房间查询按类别惰性缓存，并共享同一结果；不要求每 tick 主动扫描所有无用类别。
3. 区分已就位、在途、孵化中、即将退役的能力；防止把未来产能当当前产能。
4. 结构静态索引可以跨 tick 缓存 ID，但对象引用必须刷新；建筑/RCL/布局版本变化触发失效。
5. 无视野时提供历史情报及时间戳，不返回伪造的实时库存或据此认定建筑被毁。

**异常**：对象消失时标记 invalid；失去视野时标记 unknown，二者不能混用。

**验收**：同 tick 不重复全局角色过滤；跨 tick 不残留旧 RoomObject；远矿暂时不可见不会丢失所属 Colony。

## 3. colony：经济政策与职责协调

**输入**：Context、带完整性标签的账本摘要、业务能力和任务需求。**输出**：运行模式、人口目标、发展优先级和支援额度。

不把所有状态挤进一个枚举：`phase=bootstrap/recovery/growth/mature`、`security=normal/threatened`、`cpuMode=normal/recovery` 可以同时存在。

逻辑：

1. 判断采矿、运输、出生供能、控制器维护能否闭环。高 RCL 缺失核心岗位时同样进入恢复状态。
2. 区分理论来源、实际采收、实际运达和可动用库存。数据不足时输出估计与置信度，不使用“没有观测到收入=零收入”。
3. 先计算关键岗位未来续代费用、紧急补给和必要维修，再分配建设与升级的长期能力目标。
4. 对已有积压计算可执行的库存消化方案：能源在哪里、运得动多少、还有多少有效工作、会占多少出生/CPU。慢速库存变化不触发单位每 tick 停工。
5. 根据工地价值、剩余工程和瓶颈配置建设与升级人口；建设结束或关键工地出现时即时重算，不等低频周期。
6. 向任务层报告可提供的支援资源；本地核心续代需求优先得到保障。

新增预算控制只影响后续人口、任务归属和补给排序。已有有能量的合法 WORK 持续执行；长期储备不足通过减少未来扩编、续代体型和明确的任务调整纠正，不能藏入 actionAllowed 的数值门槛。

**频率**：每 tick 轻量健康判断；经济重算事件触发，约 100 tick 兜底，最终按实测 CPU 校准。

**验收**：RCL4 全矿工死亡能恢复；有库存和有效工程时允许消费库存；缺测不造成出生/用工反复切换；升级器没有人为轮休。

## 4. mining：矿点、岗位与交接

**输入**：归属矿点、合法矿位、可用矿工、路线和设施。**输出**：矿工能力请求、矿区供给、设施需求和采矿动作。

每个 source 有稳定 operationId，绑定 Colony 与 sourceId。固定的是矿点职责，不强制把所有 hauler 永久绑定单矿。

逻辑：

1. 根据 source 实际类型/容量/再生规则和可用站位估算采收能力；分别报告理论、在位与未来接班能力。
2. 缺岗或续代缺口向 workforce 提交唯一 slotKey 请求。
3. 接班时间包含待排队、出生、行程和合法交接；单矿位下，接班者先等待在不挡路的位置，旧矿工在接班者可到位时让位。
4. 矿工能合法采集时继续工作；根据设施向 container/link 交接或落地，动作组合遵守游戏规则。
5. 容器缺失发布建设需求，同时采用合法的临时交接；满箱/地面堆积上报 logistics 与 colony，不能直接推断为“缺 hauler”。

**持久状态**：sourceId、home、seat、assigned、replacement、最近已确认交接；不复制完整 source 对象。

**验收**：两个矿工同时到期、唯一矿位交接、容器消失、远矿撤离；没有重复接班出生或把在途 WORK 当实采。

## 5. logistics：供需、预约和运输

实现契约：`creep.memory.haul={state,task,origin}`；state为idle/pickup/deliver。task保存目的地id、source、amount、pickupAmount、priority、expires和必要的port/intent。实际货量每tick读取creep.store；intent只表示本tick接受，下一tick按真实库存核对。prepare按载货优先统一分配，普通评分变化不使在途任务掉头；旧多套标志只做一次迁移。临时工退出运输时释放数量与卸货口预约。


**输入**：统一供给/需求表、当前 cargo、节点与合法卸货口、路线成本。**输出**：hauler 工作、轻量预约、运输能力缺口。

逻辑：

1. 汇总矿区/仓库/遗物等可取资源，以及出生、防御、控制器、施工节点的需求。双向缓冲区按本次流向发布请求，避免源与目标相同或取回刚送到的能源。
2. 先延续合法任务，再给未分配单位选择任务。分配依据紧急等级、距离、交付量、源侧溢出风险和任务年龄；轻微分差不会使在途单位反复掉头。
3. 源端和目标端分别预留；跨 tick 任务重建当 tick 预留表。空载未来取货为软承诺，已装载货物及当 tick 已接受意图优先保留。
4. 统一处理取消、抢占与过期，由 logistics 修改自己的任务记录，业务模块不直接改别的 creep 预约。
5. 运输状态为 `取货→运送→卸货→下一任务/停车`。空取货点、目标被毁、不可达和真实停滞分别处理；疲劳及合理等待不记成堵塞。
6. Controller Container 始终按实际空位发布需求；停工风险影响配送优先级。普通缓冲不要求全部 hauler 先灌满一个节点。
7. 已在合法相邻位置即可卸货，无需绕行到指定口。单次额度以现有 cargo 和本 tick 尚未被已接受交付占用的物理空位为准；旧预约不截断整批交付。超过旧预约的交付同步缩减其他未执行承诺。
8. 多卸货口采用短期占位，卸完让出入口；普通任务满载并非唯一出发条件，供给耗尽或紧急交付时允许部分载荷出发。

运力初算：`所需 CARRY ≈ ceil(Σ(线路流量 × 完整往返时间) / CARRY_CAPACITY)`。完整时间包含空载、重载、装卸、路况；之后用真实往返与交付观测修正。积压需区分缺运力、缺卸货口和缺消费能力，不能无限追加 hauler。

**验收**：两车争同一库存/空位、旧预约小于当前车载、目标被毁、工地补给过期、不同矿区竞争、Link/仓库能源回流循环。

### 5.1 主房 W21N26 的具体运输示例

以下实物数据来自 HTTP API 诊断快照 tick **73990902**；当次代码回读确认远端 12 个模块与本地一致。它是一张单 tick 快照，不代表这些库存持续不变，也不是长期吞吐验收。完整快照保存在同目录 `screeps-logistics-example-W21N26.json`。

| 节点 | 位置 | 快照能源 | 物流身份 |
| --- | --- | --- | --- |
| 矿点 A 的 Container | (25,25)，source 在 (24,24) | 10/2000 | 原料供给 |
| 矿点 B 的 Container | (17,41)，source 在 (16,42) | 0/2000 | 有能源时提供原料 |
| 矿点 B 的 Source Link | (16,40) | 80/800 | Link 网络发送端 |
| Hub Link | (25,28) | 106/800 | Link 网络接收端、Hauler 取货点 |
| Spawn 与 30 个 Extension | Spawn 在 (21,28) | 合计 1800/1800 | 出生能源消费端，当前无缺口 |
| Controller Container | (16,23) | 220/2000 | 升级补给消费端，物理缺口 1780 |
| Storage | (24,29) | 18630/1000000 | 可供给、也可接收盈余的缓冲库 |

角色权限由用途决定：常规 hauler 不从 Spawn/Extension 或 Controller Container 抽走能源。Controller Container 的能源由升级工消费。Storage 可以双向流动，但每个运输任务必须有两个不同节点；不能为了填仓库又从同一仓库取货。

**当前实现怎样选择：**

1. `haulTarget()` 先选择配送目的地。顺序为 Spawn/Extension → Tower → 紧急控制器补给 → 施工补给节点 → 普通控制器补给 → 符合条件的其他 Link → Storage。需求量减去其他车有效的送货预约；同级优先延续原任务，再看距离。
2. `collectHaul()` 保留合法旧取货目标；需要重选时，在掉落、矿边 Container、墓碑/废墟、Hub Link 中评分。评分近似为 `min(来源能源, 车的空位)/(车到来源距离+3) × (1+源侧库存压力/500)`，没有计算完整的取送路线，也没有扣除其他车计划取走的能源。
3. Storage 目前只作为兜底：上述正常候选全部没有、车辆完全空载且已有送货任务时，才考虑从 Storage 取货。因而“仓库有很多能源”不意味着现有逻辑马上会取仓库。
4. 车辆达到容量的 90%，或者已拿够本次配送预约量，就进入送货；当前取货无法继续而车上有货时也可转送。目的地在每 tick 重新验证，同级倾向保留，出现更高优先需求或失效可以重选。
5. 到目标后按实际可装下的能源卸货，不受旧预约数量截断。代码记录的 pickupAmount/sent 是已接受意图的预计量，真实交付仍要看结算。

快照中的三个实际任务：

| 车辆名尾号 | 当前状态 | 已记录的运输路线 |
| --- | --- | --- |
| 73990859 | (18,25)，携能 90/100，配送中 | 已取货 → Controller Container (16,23) |
| 73989395 | (17,24)，携能 0/100，取货中 | Hub Link (25,28) → Controller Container (16,23) |
| 73990221 | (24,26)，携能 116/350，取货中 | 矿点 A Container (25,25) → Controller Container (16,23) |

另外两辆车也选中了矿点 A 的同一个 Container。当前只有目的地额度/卸货口预约，没有共享取货数量预约，因此三车可以同时选择可见库存只有 10 的来源。快照中各车的 pickupAmount=10 是意图记录，不能加起来声称采集了 30。这张快照也不能单独证明长期停滞。

**新设计如何明确决定“从哪取、送哪去”：**

1. 先生成节点供需表。以该快照为例，出生节点需求是 0；Controller Container 可接收 1780；矿 A 可取 10；Hub 可取 106；Storage 提供当前可用、未被明确任务占用的库存。源端未来产量另作预测，不冒充现货。
2. 先调度已经携货的车：已有合法交付任务通常直接继续；是否补装必须比较额外路程和交付期限，不为了“必须满载”延误紧急补能。
3. 对空车，在最高优先且尚未被覆盖的需求中，比较完整的“车→来源→目的地”组合。Storage 与矿区、Hub 一起参加比较；依据可交付量、缓存路线时间、目标断粮期限及源侧溢出风险选择，不只比较车到矿的距离。
4. 一旦分配，源端与目标端一起预约。`可取现货 = 当前库存 − 其他车有效取货预约`；`尚待配送 = 当前需求 − 有效送货承诺`。当前 cargo、已提交意图和空载未来承诺分别处理，不能双重计数。
5. 对矿 A 的 10 能源最多承诺总计 10 的现货；Hub 的 106 同样不能同时承诺给两辆各取 100 的车。其他车可选择 Storage，或执行其他需求；有用的 10 能源仍可运输，不设置最低取货批量。
6. 更高优先紧急需求、实际取空/装满、节点消失、道路失效、任务超期才触发改派；普通小幅评分变化不让在途车掉头。取送后用下一 tick 的实际状态释放/修正预约。
7. Spawn/Extension 出生后出现缺口，下一轮生成补能请求。正常消费需求已覆盖时，才把需要腾空的矿区/Hub 盈余送入 Storage。系统不强制“所有矿都先入 Storage”，也不把 Storage 永久排除在主动供给之外。

例如一辆空车就在 Storage 旁，Controller Container 有未覆盖需求，矿边只有已被其他车预约的 10：新规则会直接安排 **Storage → Controller Container**，无需绕路排队取矿。若同等条件下 Hub 的未预约现货距离更近且足够，则选 **Hub → Controller Container**。准确最优组合还需要路线和占用信息，不能只用此快照的直线距离宣称已算出最优。

上述是具体化后的拟议规则，尚未替换线上逻辑。

## 6. workforce：唯一出生管理器

**输入**：所有业务和 Mission 的 WorkforceDemand、岗位能力、身体约束、出生时间线与供能。**输出**：出生意图、排队原因、实际在产记录。

逻辑：

1. 以 owner + slotKey 去重；死亡、任务取消、出生中与在途接班一起计数。
2. 按未来时间线计算岗位覆盖，得到最迟开工时间：岗位需要时间减去新身体孵化、行程和交接时间。已有排队工作纳入可排入性判断。
3. 先恢复已经断掉的生命线，再安排临近期限的关键续代/防御/控制器维护，再补有效产能和已批准任务。相同紧急等级比较期限与等待时间。
4. 身体选择同时考虑即时恢复、预计有效产能、路线/站位、寿命与出生占用，不默认总是花满容量。
5. 能源不足时：救急使用能恢复闭环的廉价身体；普通请求保留并输出等待原因。可安排不会挤占关键请求期限和已预留资金的其他请求。
6. 多 spawn 共享房间能源预留及需求去重；同一 spawn 成功提交后本 tick 不再提交另一项。
7. 接受出生意图与下一 tick 真实在产分别记录；失败/重置后重新确认，避免凭名称永久认定出生成功。

CPU 恢复限制只用于有证据的新增可选负载；关键岗位替补保持保护。已批准的 Mission 同样走此队列，expansion 不再直接调用 spawnCreep。

**验收**：全灭但有 spawn、双矿同步续代、多 spawn 共用能源、低价任务长期饥饿、取消 Mission、global reset 后出生去重。

## 7. development：升级、建设与必要维修

**输入**：ColonyPolicy、已审核 ConstructionRequest、当前工地/建筑/工人、控制器状态。**输出**：WORK 需求、补给需求、工人分配和工作动作。

升级逻辑：

1. 防降级是独立紧急目标，不能因为没有仓库或正常升级人口不足而失效。
2. 根据当前可用节点和合法席位安排稳定站位；席位外的工人只有在实际可工作且不挡运输时才计入有效能力。
3. 供给设施被毁时撤销失效绑定，改用其他可用补给或移动升级，并请求修复/重建。
4. 已有能量且在范围内就升级；RCL8 等真实游戏约束单独处理。单次返回 OK 不作为实际升级量。

建设逻辑：

1. 接收 planner 的布局候选及 mining/mission 的语义需求，把后者映射到合法计划项；统一成为 createConstructionSite 的调用方。
2. 校验 RCL、建筑数量、地形冲突、依赖关系和启用状态；Rampart 请求过滤。新房首 spawn 也必须通过此入口。
3. 优先修复生产闭环和必要防御设施，再建设能解除当前瓶颈的扩容/道路/补给节点；同等价值时考虑剩余工程和路程。
4. 按工地可达、可补能和工人能力开放并行工作，避免工人集中拥堵；不新增固定“三个工地”之类人数无关的上限。
5. 工人持有少量能源也能继续施工。只有目标完工、失效、紧急抢占或持续不可达才改派。
6. 对即将完工的工地协调剩余工程量，避免多个单位对同一剩余量重复规划；未被分配到有效工作量的工人转其他有用任务。

维修逻辑：根据建筑用途、受损程度、衰减和断链风险发布工作；已有 Rampart 按单独的防御目标维护。没有必要维修时不为提升指标消耗能源。

**频率**：动作每 tick；工地完成、建筑消失、RCL改变时立即重算；候选工地复查低频兜底。常规建设结束后，可用工人进入升级或其他明确任务，不遗留重复身份。

**验收**：有能量 builder 连续工作、少量能源不强制补满、Container 消失、工地刚完工、无工地转岗、Rampart 全路径停建。

## 8. defense：威胁与本地保护

**输入**：敌人有效部件/位置、受损单位、塔与能源、关键设施、安全模式状态。**输出**：威胁等级、塔动作、撤离/防御请求和紧急补给。

逻辑：评估实际伤害与治疗能力及关键设施风险；协调塔火力、治疗与必要维修；发布撤离或防卫人口需求。安全模式申请由全局轻量仲裁核验游戏限制与真正需要保护的房间，再交执行器提交；不能由多个房间盲目竞争。

无视野不等于安全。紧急避险可显式抢占经济任务，任务所有权随之转移；生产逻辑不能在后面把撤离动作覆盖。平时维修和战斗耗能分别记账。

**频率**：每 tick；威胁能力分析使用当 tick 共享数据。

**验收**：友方受伤、敌方治疗、塔缺能、两个房间同时求援、矿工撤离、普通经济模块失败不影响塔动作。

## 9. links：房内能源网络

**输入**：已建 Link 及规划标签、库存/冷却、节点需求、当 tick 资源占用。**输出**：Link 意图、接收节点的后续物流供给和损耗预期。

逻辑：

1. 优先按已审核标签识别 source/remote-receiver/hub/controller 角色；标签缺失时用保守几何回退并报告不确定性。
2. 根据节点紧急需求与实际空位选择传输，记录发送与接收占用；明确每段网络方向。
3. 与 logistics 协调同一 Link 的 withdraw/fill/send，避免重复使用同一份初始能源或重复占用空位。
4. 不假设本 tick 刚收到的能源已经能再次发送或被取走；以初始快照及游戏动作规则为依据。
5. 降级、冷却或节点消失时允许物流采用已有合法替代通路；下一 tick 校验实际结果，损耗交 ledger 记录。

外矿入口中继只在真实路线、吞吐和 RCL 配额支持时启用，不为了填满 Link 上限而新建。

**验收**：两输入争一接收口、Hub 同 tick 取货与发送、源 Link 满载、节点消失、controller 普通补给与 spawn 紧急需求竞争。

## 10. planner / plans：布局与执行档案

**输入**：本地审核布局、真实地形/既有建筑、controller 与 archive ID、启用配置。**输出**：合法的分 RCL 计划、道路/矿位/升级席位/物流口及 ConstructionRequest。

逻辑：验证版本和房间身份；保留既有可复用设施；按 RCL 校验数量、可达、运输接口与依赖；给 development 提供建设候选。完整选址与防线优化仍在本地做；运行时只做有限差异检查和必要恢复。

只有与静态归档精确匹配的冷房计划能压缩成摘要；激活时恢复准确坐标。归档缺失或版本不匹配时保留原数据并报错，不能删除后临时猜布局。

Rampart 坐标可以留在计划里，建设启用状态必须为 false，并由 construction 入口再次过滤。规划模块不直接创建工地，不直接安排 creep，也不把缺少高级建筑布局等同于当前房间无法恢复。

**频率**：激活、版本、RCL和建筑变化触发；轻量差异检查可沿用约 10 tick 兜底。

**验收**：global reset、冷房激活、变更未归档、既有建筑冲突、Rampart 停建、计划完成不被误报为已建完成。

## 11. expansion / missions：情报与有终点的任务

**输入**：带时间戳的情报、候选布局摘要、路线、各 Colony 支援能力和现有扩张政策。**输出**：任务状态、出生/运输/建设需求。

情报只记录可见事实、来源和 lastSeen；侦察不顺手同步跑完整布局搜索。候选分别评估资源、路线、出生支援、风险和 CPU；历史安全判断必须过期重验。

开拓状态：`candidate→scouting→ready→claiming→bootstrapping→stabilizing→complete`；异常为 `paused/blocked/aborting`。每个状态有进入条件、进展证据、任务期限和恢复办法。ready 是内部条件通过，不是自动要求用户逐次批准。

任务统一申请 claimer/pioneer/支援能源和首 spawn 工地。首 spawn 建成后显式交接人员与人口管理给新 Colony，母房停止无依据的重复补人；达到“本地采运、控制器维护、实际自主出生及续代可行”后才 complete。暂时缺能与目标被他人占领必须使用不同异常原因。

已有并发开拓数、房间数、支援授权限制迁移为命名政策，集中配置；本轮重构不自动扩大扩张范围。预留救援等任务接口，未获授权的进攻/市场功能不激活。

**频率**：活跃单位与紧急任务变化每 tick；候选评分低频、错峰；已有遥测只能作带年龄的输入。

**验收**：首 spawn 建成但经济未自给、claimer 在途失去视野、目标被占、母房缺矿工、任务取消释放预约、交接不重复接管。

## 12. movement：房内与跨房移动

**输入**：唯一任务所有者的目标/范围/优先级、地形和结构、路线情报。**输出**：move 意图、真实移动进展、阻塞原因。

逻辑：统一原 runtime.go 与 expansion.travel 的路线/缓存/失败处理；优先复用路径，仅目标、结构版本、风险变化或连续真实失败时重算。跨房明确要求出口 tile 本身可通行，抵达出口相邻位置不算通过。

区分疲劳、正在工作、合法等位与实际尝试移动失败；只对后者累积卡位计数。矿位、升级席位、卸货口和关键路口共享少量占位信息，优先做局部让位，保留现有有效的 moveTo 复用。不默认引入全图多单位寻路器。

同一单位每 tick 的最终移动指令统一提交，避免采矿/运输/避险互相覆盖。必要移动必须在可选重计算之前完成，不能把全部移动拖到一个可能被 CPU 截断的收尾阶段。

**验收**：沼泽疲劳、动态占位、出口建筑阻挡、原地驻守、无视野路线、任务正常完成换目标不被误报震荡。

## 13. ledger：真实能源账本

**输入**：上一 tick 的事件、前后库存、对象/工地归属、实际出生与跨房运输。**输出**：实际采收/使用/转移/损耗、窗口指标、覆盖率和未知项。

逻辑：每 tick 独立结算上一 tick；区分内部搬运和外部输入；死亡、工地完成、跨边界 cargo 保留最小必要归因。OK 只证明意图被接受，不能替代实际事件。缺测不填零、残差不等同浪费。

沿用现有 U/G/eta 定义和 300/1500/6000 窗口。库存变化、进口、Link 损耗和计划外建设单列；必要孵化/维修/塔耗能计入 U，但不能为提高 U 制造无效花费。

房间物理账本继续可用；未来 Colony 含外矿时必须新增明确汇总范围，避免跨房运输在两边重复计入收入。外矿归因与视野覆盖未完成前，标记该口径不可用于自动能效验收，而非直接扩大理论分母。

CPU/Memory 压缩使用经过对照验证的定长聚合，不简单缩掉窗口或删除历史。schema 迁移保留旧有效窗口；新字段预热，不能伪造过去样本。

**验收**：运输者跨房/死亡、同 tick 工地完工、reset/缺测、临时外援、库存透支、意图失败、旧新聚合窗口逐项对齐。

## 14. monitor / metrics：诊断与可观测性

**输入**：模块结果、账本、Context、CPU/移动计数。**输出**：有界遥测、告警、策略原因及性能归因；不直接操控人口或角色。

每 tick 轻量累计；维持约 20 tick 摘要发布。按房间/模块/角色记录 CPU，区分 Memory 解析与业务成本。记录目标切换时区分正常完成和失败重选；只保存所需的聚合和少量样本。

每项出生或不出生、任务暂停、运输重选和模式变化都能找到 reason 与证据年龄。告警区分“能力估计不足”“已确认停工”“统计不可用”；持续性用于减少噪声，明确缺矿工等故障不必等待完整能效窗口。

有能源积压时，诊断按采集、取货、移动、卸货、消费、续代和口径依次检查，不能把一个指标直接变成单一修复策略。监控故障不得阻断经济执行；线上代码不自动调用 Codex 或恢复暂停的定时任务。

**验收**：告警去重与恢复、数据 tick 停止、同症状不同原因、监控异常、Memory 有界、仪表盘兼容。

## 迁移与验证顺序

1. 锁定真实实现基线与文件负责人；先拆接口和调用边界，保留行为回归。此设计阶段没有接管运行代码或发起部署。
2. 完成 RoomContext、Colony 输出和唯一 spawn 入口；旧模块通过适配层提交请求。检查调用图中不存在双重执行路径。
3. 分离 mining、development、defense、links、movement；集中 construction 和任务归属。每次迁移只切换一个明确职责。
4. 更换 logistics 分配和 workforce 队列；用真实场景多 tick 回放和现有经济测试验证。影子计算只能产出比较结果，不能提交第二套动作。
5. 接入任务/外矿接口；只有账本归属和覆盖通过后才启用相应业务评价。新增业务另按既有授权和验收推进。
6. 压缩/迁移监控和 Memory；保持旧窗口与仪表盘一致，执行可回退 schema 迁移。

验收至少覆盖：无矿工恢复、双矿续代、单矿位交接、多车抢空位、全部卸货口暂占、Controller Container 消失、工地完成与转岗、两个房间同时异常、出口阻挡、reset、缺测、Rampart 全入口停建和多 spawn 能源冲突。

性能比较使用相同输入回放，并在线比较相近单位数、RCL和运输工作量下的完整窗口；观察平均/峰值 CPU、bucket 趋势、Memory、实际交付、源侧积压和成长。现有离线检查通过不等于性能提升或线上吞吐通过。本审阅稿未运行行为测试，因为尚无实现改动。
